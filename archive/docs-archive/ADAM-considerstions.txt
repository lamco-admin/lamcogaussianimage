people didn’t just swap Adam out; they’ve mostly bent Adam to be more Gaussian-aware, made it sparser/fused for speed, or replaced it with second-order solvers that still sit in the same training loop.

I’ll break it down by “what changed compared to vanilla Adam in 3DGS”.

1. What “plain Adam” looks like in original 3DGS

The original 3D Gaussian Splatting codebase uses pretty stock Adam, but with per-parameter-group learning rates and a special schedule for positions:

One Adam optimizer with different lr for:

positions, scales, rotations, opacity, SH features

Position LR follows a delayed schedule (Plenoxels-style) that starts small, ramps up, then decays. 
GitHub

This already exploits the fact that “position” is touchier than “color”, but it’s still just first-order Adam on dense tensors.

2. Sparse / fused Adam for speed (Taming-3DGS, LiteGS, etc.)

A big line of work keeps Adam but makes it cheaper per step:

Taming-3DGS / official 3DGS “sparse_adam”

Introduces a SparseAdam variant that only updates Gaussians that actually contributed to the rendered pixels in that batch.

Combines this with a fused Adam kernel (one CUDA kernel per tensor) so you don’t launch tons of tiny Adam kernels. 
arXiv
+2
GitHub
+2

Integrated into the official repo as --optimizer_type sparse_adam, giving ~1.6× training speed-up at basically the same visual quality. 
radiancefields.com

Conceptually: same Adam math, but sparse parameter updates + better kernel packing → faster iterations without changing the loss or densification logic.

3. “Better Optimized Gaussian Splatting” (BOGausS) – Adam that knows about geometry

BOGausS explicitly modifies Adam itself to be more aware of Gaussian geometry and state. Key tweaks: 
Eusipco 2025
+1

Precision-aware step scaling (∆θ)

They estimate a confidence/precision per Gaussian (from camera geometry), and use that as a scaling factor ∆θ in the Adam update for positions and sizes.

Intuition: if a Gaussian is poorly constrained by views, don’t let Adam fling it around; if it’s well-constrained, you can step more aggressively.

Linear parameterization for sizes (σ instead of log σ)

Original 3DGS uses log-σ to let sizes grow/shrink exponentially; this can create exploding “needle” Gaussians.

BOGausS moves to linear σ, but couples it with precision-aware scaling so it’s still stable.

Unbiased Sparse Adam with per-Gaussian “time”

When you do sparse updates, some Gaussians don’t get gradients every step, so the usual Adam bias-correction (based on global step t) becomes wrong.

BOGausS keeps a separate step counter per Gaussian, and only increments it when that Gaussian is updated, which restores the correct bias-correction for the moving averages.

State inheritance after splitting

Instead of resetting optimizer state when a Gaussian is split, they partially copy/scale the parent’s Adam moments (m, v) and time t into the children.

That avoids the “newborn Gaussians with no history” problem and improves convergence/stability after densification.

Rate–distortion-style densification/pruning

They also change which Gaussians are split/pruned using PSNR-based criteria tied to each Gaussian’s contribution to error. This isn’t Adam per se, but it radically changes the optimization landscape.

Result: 0.5–1 dB PSNR improvement and smoother behavior, especially in difficult scenes, at similar or lower cost compared to vanilla 3DGS with standard Adam. 
Eusipco 2025

4. Second-order replacements for Adam (LM / Gauss–Newton style)

Another branch says: Adam is fine, but we can do better if we approximate curvature.

3DGS-LM (ICCV 2025) – LM instead of Adam

3DGS-LM literally replaces Adam with a custom Levenberg–Marquardt optimizer:

Uses LM with a custom GPU Jacobian-vector product cache to compute Gauss–Newton steps on the Gaussian parameters.

Still uses the same differentiable rasterizer and densification logic as 3DGS. 
arXiv

Reports ≈20–30% shorter training time vs Adam (and vs Taming-3DGS) at similar PSNR/SSIM/LPIPS. 
ChatPaper

LM-IS: LM + importance sampling (Pehlivan et al. 2025)

Even more aggressive: a matrix-free LM with importance sampling: 
arXiv

LM solved via GPU preconditioned conjugate gradient with Jacobian–vector products (no full Jacobian stored).

View clustering to choose diverse camera batches → better curvature estimates.

Pixel-wise importance sampling (samples pixels with higher loss more often).

A learning-rate heuristic that constrains maximum color change per step, instead of line search.

They benchmark against Adam, RMSProp, and SGD+momentum and show:

Similar or slightly better PSNR/SSIM than Adam,

Up to ≈6× faster convergence in some settings. 
arXiv

So here the “adaptation” is: swap first-order Adam for a second-order Gauss–Newton/LM solver that’s engineered to be GPU-friendly.

5. Structural regularization that changes how Adam behaves

Not strictly new optimizers, but methods that change the gradient statistics Adam sees:

DropGaussian (structural dropout on Gaussians)

During training, randomly drop a fraction of Gaussians (like dropout on primitives), especially in sparse-view regimes. 
arXiv

This:

avoids overfitting a few near-camera Gaussians,

boosts gradients for far/poorly-seen Gaussians,

improves sparse-view PSNR with almost no extra compute.

Adam is still the optimizer, but now it’s working on a stochastically thinned set of primitives, which acts like a structural regularizer.

Depth / spectral / shape regularization

Methods like Depth-regularized 3DGS, Spectral-GS, shape-selective splatting, etc., add losses or splitting criteria that are sensitive to:

scene depth / geometry,

spectral entropy of the covariance,

Gaussian shape. 
arXiv
+1

Again, Adam itself isn’t changed, but the loss landscape and densification rules are, which indirectly fixes issues like needles, floating artifacts, and overfitting.

6. Feed-forward / hybrid setups that reduce reliance on long Adam runs

There’s also a trend to front-load most of the work into a network and use Adam as a short fine-tuning stage:

pixelSplat, MVSplat, FreeSplat and similar models directly predict Gaussian parameters from images via a CNN, then optionally fine-tune with a few optimization steps. 
arXiv

From an optimization perspective, this is like replacing “30k Adam iterations” with “a forward pass + 2k Adam iterations”, so Adam’s role becomes light fine-tuner instead of heavy workhorse.

7. What this means if you’re designing your own optimizer

If you want to riff on the Adam-in-GS story, the patterns that have actually worked in the literature are:

Geometry-aware scaling

Scale steps using some notion of confidence/precision per Gaussian (BOGausS style).

Treat position/scale differently from color/SH, possibly with separate LRs and schedules.

Sparse + fused updates

Only touch Gaussians that contributed to the batch.

Use fused kernels so Adam isn’t your bottleneck.

Stateful densification

Don’t throw away optimizer state on split/prune—inherit or reuse it.

Curvature where it matters

Consider an LM / Gauss–Newton step (even approximate) when the primitive count is moderate.

Use importance sampling and view clustering to keep second-order methods tractable.

Structural regularizers, not just L2

Randomly disable subsets of Gaussians (DropGaussian-style),

Add depth/shape/spectral regularizers that tame “needle” and “floating” artifacts.

6. A simple optimizer loop template

Very roughly, something like this for your encoder:

params = init_gaussians(image)    # few, large ones
adam_state = init_adam_state(params)

for iter in range(T):
    # 1) Render and compute loss
    recon = render_gaussians(params)
    distortion = mse(image, recon)   # or SSIM
    rate = rate_proxy(params)        # per-gaussian cost + quantization model
    loss = distortion + lambda_rd * rate

    # 2) Backprop to get gradients
    loss.backward()
    grads = get_gradients(params)

    # 3) Confidence / sparse selection
    error_map = (image - recon).abs()
    active_pixels = topk_pixels(error_map)
    active_gaussians = gaussians_touching(active_pixels)

    # 4) Adam update *only* for active gaussians,
    #    with per-gaussian time and confidence scaling
    for g in active_gaussians:
        adam_state[g].t += 1
        adam_state[g].m = beta1 * adam_state[g].m + (1 - beta1) * grads[g]
        adam_state[g].v = beta2 * adam_state[g].v + (1 - beta2) * grads[g]**2

        m_hat = adam_state[g].m / (1 - beta1**adam_state[g].t)
        v_hat = adam_state[g].v / (1 - beta2**adam_state[g].t)

        s = confidence_scale(g)   # based on support / gradient energy
        params[g] -= lr_group[g] * s * m_hat / (v_hat.sqrt() + eps)

    # 5) Periodic: split, merge, prune, and re-solve colors
    if iter % split_every == 0:
        split_some_gaussians(params, adam_state, error_map)
    if iter % prune_every == 0:
        prune_bad_gaussians(params, adam_state, lambda_rd)
    if iter % color_refit_every == 0:
        refit_colors_closed_form(params, image)


Obviously you’d implement this more efficiently, but algorithmically this is the shape of a “Gaussian-aware Adam” for 2D codec fitting.
